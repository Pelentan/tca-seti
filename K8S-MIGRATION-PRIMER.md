# TCA / SETI / AC — Kubernetes Migration Primer

**Purpose:** Reference document for K8s deployment of TCA constellations on k3d with Traefik ingress.  
**Current State:** SETI and TCA Vox are both fully operational on a shared k3d cluster named `tca` with Traefik ingress. Both constellations accessible at `https://*.tca.local`.  
**Status:** Migration complete for dev environment. Production decisions documented as open items.

---

## What Was Decided and Implemented

These decisions are final and reflected in the current codebase.

**k3d for local development.** k3s running inside Docker containers. Spins up in seconds, supports multiple nodes, loads local images without a registry, tears down cleanly. The inner dev loop stays fast.

**Helm over raw manifests.** Templating collapses repetition across Job deployments. Per-environment values files (dev/staging/prod) without duplicating manifests. Dependency management for cert-manager, Redis, PostgreSQL.

**Shared cluster, namespace isolation.** SETI runs in the `seti` namespace, TCA Vox in the `tca-vox` namespace. Both share the `tca` k3d cluster and the `tca-registry:5000` local registry.

**Per-constellation cert-forge.** cert-forge is not cluster-level. Each constellation has its own cert-forge instance, its own CA, and its own cert material. Different constellations may have different security requirements, CA backends, and cert lifetimes. Centralizing PKI collapses that flexibility. Centralizing cert-forge would also mean a cert-forge restart breaks every constellation simultaneously.

**Traefik TLS termination pattern.** Traefik handles browser-facing TLS using a cert generated by cert-forge for the constellation's external hostname. The backend connection from Traefik to the gateway is standard TLS (not mTLS) — Traefik is inside the cluster and already under operator control. The gateway uses its cert-forge instance cert (with the external hostname in the SANs) for this connection. In dev, Traefik uses `insecureSkipVerify: true` for backend verification — see production open items.

**cert-forge generates Traefik TLS secrets.** cert-forge writes two additional K8s resources for each constellation's Traefik integration: a `kubernetes.io/tls` Secret (`{constellation}-traefik-tls`) containing the external hostname cert for Traefik TLS termination, and an Opaque Secret (`{constellation}-traefik-ca`) containing the constellation CA cert for backend verification. These are configured in `forge.json` via `tls_secret` on the static cert entry and `traefik_ca_secret` at the top level.

**Automatic cert rotation.** cert-forge manages automatic rotation of both instance certs and the constellation CA on a 30-day interval. Rotation is configured in `forge.json` under the `rotation` key. The rotation list contains only stateful workloads that do not roll naturally on their own (Mongo instances, PostgreSQL, Redis). Everything else picks up new certs the next time it rolls for any reason. CA rotation uses a configurable overlap window (default 24h) during which both CAs are trusted, preventing hard failures mid-rotation.

**imagePullPolicy: Always on all deployments.** Mutable tags (`dev`) require `Always` pull policy or the cluster will run stale images after a push. All SETI and Vox deployment templates have this set.

**K8s network policies replace Docker Compose network isolation.** The ac-net architecture (AC joins a shared network with all services) maps directly to K8s NetworkPolicy objects.

**StatefulSets for persistent workloads.** PostgreSQL and Mongo instances use StatefulSets. Redis uses a Deployment with AOF persistence.

## Cluster Setup

```bash
# k3d cluster create — shared cluster for all constellations
k3d cluster create tca \
  --registry-create tca-registry:0.0.0.0:5000 \
  --agents 2 \
  -p "80:80@loadbalancer" \
  -p "443:443@loadbalancer"

k3d kubeconfig merge tca --kubeconfig-merge-default
```

Traefik is installed by k3d automatically. Both port 80 and 443 are exposed. All constellation ingress uses port 443 (websecure entrypoint).

### /etc/hosts entries required

```
172.18.0.2  seti.tca.local
172.18.0.2  vox.tca.local
```

The IP is the k3d load balancer IP — verify with `kubectl get service traefik -n kube-system`.

### Ingress files

Located in `k3d-cluster/ingress/`. Each constellation has one ingress file containing a `ServersTransport` and an `IngressRoute`.

```bash
kubectl apply -f k3d-cluster/ingress/seti-ingress.yaml
kubectl apply -f k3d-cluster/ingress/vox-ingress.yaml
```

The browser will warn about the cert — the constellation CA is self-signed and not in the OS trust store. This is expected in dev. Import the constellation CA cert into the browser trust store to suppress the warning.

## Helm Chart Structure

One chart per constellation. No shared library chart — the repetition across Job deployments is handled by Helm templating within each chart.

```
charts/{constellation}/
  Chart.yaml
  values.yaml              # base values — tags are "latest", external hostnames are ""
  values/
    dev.yaml               # k3d overrides — tags are "dev", externalHostname set
  templates/
    namespace.yaml
    cert-forge/            # deployment, service, serviceaccount, role, rolebinding
    gateway/               # deployment, service
    {job}/                 # deployment per Job
    configmaps/
    network-policies/
```

### Key values

```yaml
# values.yaml — base
gateway:
  tag: latest
  port: 4000
  externalHostname: ""     # empty = no GATEWAY_EXTERNAL_HOSTNAME env var injected

# values/dev.yaml — k3d overrides
registry: tca-registry:5000
imagePrefix: seti-
gateway:
  tag: dev
  externalHostname: "seti.tca.local"
```

## cert-forge K8s Integration

### forge.json — full dev example (SETI)

```json
{
  "ca": {
    "common_name": "seti-ca",
    "organization": "SETI",
    "country": "US",
    "key_bits": 4096,
    "valid_days": 3650,
    "backdate_minutes": 5
  },
  "traefik_ca_secret": "seti-traefik-ca",
  "services": [
    { "name": "star-gazer", "sans": ["star-gazer", "localhost"] },
    { "name": "seti-traefik", "sans": ["seti.tca.local"], "tls_secret": "seti-traefik-tls" }
  ],
  "output_dir": "/certs",
  "key_bits": 2048,
  "valid_days": 3650,
  "rotation": {
    "instance_interval_days": 30,
    "ca_interval_days": 30,
    "ca_overlap_hours": 24,
    "strategy": "simultaneous",
    "deployments": [
      { "name": "postgres", "namespace": "seti" },
      { "name": "redis",    "namespace": "seti" }
    ]
  }
}
```

### RBAC

cert-forge's ServiceAccount requires:
- `get`, `create`, `update` on `secrets` — for writing cert material
- `get`, `patch` on `deployments` — for rotation-triggered rolling restarts

### K8s Secrets written by cert-forge

| Secret | Type | Contents |
|--------|------|----------|
| `{constellation}-certs` | Opaque | `ca.crt`, `ca.key`, `enrollment-ca.crt`, `enrollment.crt`, `enrollment.key`, static cert files |
| `{constellation}-traefik-tls` | `kubernetes.io/tls` | `tls.crt`, `tls.key` — external hostname cert for Traefik |
| `{constellation}-traefik-ca` | Opaque | `tls.ca` — constellation CA for Traefik backend verification |

## Ingress Pattern

Each constellation ingress file contains two resources:

```yaml
# ServersTransport — how Traefik connects to the gateway backend
apiVersion: traefik.io/v1alpha1
kind: ServersTransport
metadata:
  name: {constellation}-backend
  namespace: {constellation-namespace}
spec:
  insecureSkipVerify: true   # dev only — see production open items

---
# IngressRoute — routes external hostname to gateway
apiVersion: traefik.io/v1alpha1
kind: IngressRoute
metadata:
  name: {constellation}
  namespace: {constellation-namespace}
spec:
  entryPoints:
    - websecure
  routes:
    - match: Host(`{constellation}.tca.local`)
      kind: Rule
      services:
        - name: gateway
          port: {gateway-port}
          scheme: https
          serversTransport: {constellation}-backend
  tls:
    secretName: {constellation}-traefik-tls
```

**Note:** Traefik v2 `ServersTransport` `rootCAsSecrets` requires the CA Secret to be in the `kube-system` namespace. Granting cert-forge write access to `kube-system` is a production security decision. In dev, `insecureSkipVerify: true` is used instead. The `{constellation}-traefik-ca` Secret is generated and available for production use when the security team defines the correct access model.

## Gateway Requirements for K8s / Traefik

The gateway must speak HTTPS on its external port. Plain HTTP is not acceptable in a zero-trust environment regardless of where it sits in the stack.

The gateway's instance cert must include the external hostname in its SANs. This is configured via `GATEWAY_EXTERNAL_HOSTNAME` env var, injected by Helm when `gateway.externalHostname` is set in values. The certforge client's `buildSANs` function includes this hostname alongside the standard entries (`gateway`, `gateway-{instanceID}`, `localhost`).

The external listener uses plain TLS (not mTLS) — Traefik does not present a client cert, and requiring one would add friction with no meaningful security gain given Traefik is under operator control within the cluster.

## Build and Deploy

### SETI

```bash
cd tca-seti
./scripts/build-push.sh          # builds all images, pushes to localhost:5000
helm upgrade seti ./charts/seti -n seti -f charts/seti/values/dev.yaml
```

### Vox

```bash
cd tca-vox
./scripts/build-push.sh
helm upgrade vox ./charts/vox -n tca-vox -f charts/vox/values/dev.yaml
```

### Burn-down and reinstall

```bash
helm uninstall {constellation} -n {namespace}
# wait for namespace to terminate fully
helm install {constellation} ./{chart} -n {namespace} -f {chart}/values/dev.yaml --create-namespace
kubectl apply -f k3d-cluster/ingress/{constellation}-ingress.yaml
```

### CA rotation recovery

If cert-forge restarts with a new CA (e.g., after deleting the certs Secret), all services must re-enroll:

```bash
kubectl delete secret {constellation}-certs -n {namespace}
kubectl rollout restart deployment/cert-forge -n {namespace}
kubectl rollout status deployment/cert-forge -n {namespace}
kubectl rollout restart deployment -n {namespace}
# For Mongo/stateful workloads:
kubectl rollout restart statefulset -n {namespace}
```

## Open Items — Production

These were explicitly deferred as security team decisions, not dev framework decisions.

**Traefik backend CA verification.** Traefik v2 `rootCAsSecrets` requires the CA Secret in `kube-system`. Options: (1) copy the constellation CA Secret to `kube-system` via a controlled process outside cert-forge, (2) upgrade to Traefik v3 which relaxes this restriction, (3) implement mTLS on the Traefik-to-gateway leg with Traefik holding a cert-forge-issued client cert. The `{constellation}-traefik-ca` Secret is already generated and waiting.

**cert-forge RBAC scope.** The current Role is namespace-scoped. In production, review whether cert-forge should have `patch` on Deployments, or whether rotation-triggered restarts should be handled by a separate controller with tighter scope.

**CA rotation in production.** The 30-day CA rotation interval and 24-hour overlap window are configured in `forge.json`. Production may want longer intervals or a managed CA (cert-manager, Vault, organizational CA). cert-forge's signing backend is designed to be swapped — no other Job changes.

**Staged rotation strategy.** The `staged` strategy in `forge.json` rotation config is stubbed — it falls back to `simultaneous` with a log warning. Production with many stateful workloads may want batched rolling restarts. Implementation is a clean swap point.

**Secret encryption at rest.** K8s Secrets are base64-encoded, not encrypted by default. Production deployments should enable etcd encryption at rest or use an external secrets manager.

## SETI as K8s Operator (Architecture — Not Built)

A `k8s-conductor` Job subscribing to SETI's existing feeds and translating decisions into Kubernetes API calls. This is TCA 2.0+ territory.

The observation from earlier sessions: existing tools (CAST AI, VPA) scale based on CPU. k8s-conductor scales based on understanding — it knows AC's canned query cycle from user load, knows which service is the bottleneck vs which is upstream of the bottleneck. That is a qualitatively different scaling signal.

Safety model: what changes can be made automatically vs require human confirmation? RBAC scope: minimum permissions for the decisions SETI should make autonomously. Design it before building it.
