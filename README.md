# SETI — Search for Erroneous Tessellated Interactions

A TCA constellation that monitors other TCA constellations.

SETI provides two tiers of automated testing for registered TCA applications running in a Kubernetes cluster, continuous production health verification via Contract Tests, and deep scenario validation via Plot Tests. It aggregates observability streams across all monitored applications, detects cross-application anomalies, and manages failure response policy from a single cluster-level deployment.

SETI is itself a TCA application. It registers in its own Policy Job, runs its own Contract Tests and Plot Tests on schedule, and routes its own failures through its own Interactions Job. The methodology tests itself.

---

## Architecture

SETI consists of eleven Jobs across three functional domains.

### Testing Domain

**Contract Test Job** `Go · Port 4003`
Executes tier-one tests against registered application contracts. Reads OpenAPI 3.1 specs from registered repository paths (contracts folder only), generates valid and invalid test cases, validates response shapes and status codes. Runs every 15 minutes per application in production. Stateless per run. Safe to execute against live traffic.

**Plot Test Job** `Go · Port 4004`
Executes tier-two scenario tests using AI-generated Plots. Plots describe known valid flows through an application — stateful sequences, semantic assertions, and expected inter-service call chains verified against the Signal Aggregator event stream. Runs daily per application and on deployment trigger.

**Plot Store Job** `Go · Port 4005`
Owns the Plots database. Stores versioned Plot definitions generated by Connie Wr4ngler AI partners at Job completion during application build. Tracks Plot validity against contract versions — flags Plots for regeneration when monitored contracts change.

### Observability and Delivery Domain

**Signal Aggregator Job** `Go · Port 4006`
Subscribes to `tca:events` pub/sub streams from all registered applications. The cross-application visibility layer. Feeds Plot Test call-chain verification and the anomaly detection pipeline. The only Job with multi-application event stream access.

**Feed Wr4ngler Job** `Elixir · Port 4007`
Coordinates authorized signal delivery to Wr4nglers. Receives feed requests, calls Signal Clearance for authorization, provisions scoped Redis pub/sub channels, manages connection lifecycle. Ring boss of the external delivery layer — coordinates without owning business logic.

**Results Job** `Python · Port 4008`
Owns the historical test results database. Stores Contract Test and Plot Test outcomes. Feeds trend analysis and cross-application correlation. In production, the underlying database is managed by the infrastructure team — Results Job owns the surface, the DB team owns what is behind it.

### Infrastructure Domain

**Gateway Job** `Go · Port 4000`
Single external entry point. TLS termination, JWT validation, request routing. The only Job with an externally published port.

**Signal Clearance Job** `TypeScript · Port 4001`
SETI's purpose-built authorization layer. Manages Wr4ngler clearance levels for signal feed access. Not a standard role-based User Job — clearance levels govern what signals a Wr4ngler is authorized to observe. Owned by the Sec Wr4ngler.

**Policy Job** `Go · Port 4002`
Owns the primary SETI database. Application registry, schedule configuration, failure response policy by application/Job/environment/severity, clearance definitions. Admin access only. Never externally exposed.

**Interactions Job** `Go · Port 4009` *(Stub)*
Receives structured failure escalations from Contract Test and Plot Test Jobs when policy requires human or AI intervention. Alert delivery implemented. Human-in-the-loop and AI diagnostic paths stubbed for future iteration.

**Watchdog Job** `Go · Port 4010` *(Stub)*
Security signal detection. Rogue container detection, cross-application anomaly correlation, behavioral fingerprinting. Architecture defined, implementation deferred pending security engineering input.

### Supporting Infrastructure

**UI Job** `TypeScript/React + Go · Port 4000 (via Gateway)`
Serves the SETI monitoring dashboard. Functional, no-frills SPA. Handles OIDC redirect and callback, then connects to Gateway SSE for the live observability event stream. Go static file server with OIDC callback handling; React handles everything after SETI JWT is issued.

**Integration Job** `Go · Port 4013`
Read-only versioned API for external consumption by customer tooling. Enables Grafana, Splunk, NOC displays, and internal dashboards to pull SETI data without understanding SETI internals. Clearance-scoped — service accounts see only applications they are authorized for. Versioned under /v1/ with defined deprecation policy for breaking changes.

**Observability Job** `Go · Port 4011`
Receives inter-service event reports from all SETI Jobs per `x-tca-observability` contract obligation. Sanitizes, publishes to `seti:events` Redis pub/sub. Standard TCA observability pattern applied to SETI itself.

## Key Concepts

**Contract Tests** — Tier-one production-safe tests generated automatically from OpenAPI 3.1 contracts. Validate schema conformance, status codes, required fields, and type correctness. Run on schedule. No domain knowledge required.

**Plots** — AI-generated scenario definitions describing known valid flows through a TCA application. Produced by the Connie Wr4ngler AI partner at Job completion during application build, while domain context is fully loaded. Cover stateful sequences, semantic assertions, and expected inter-service call chains.

**Plot Tests** — Tier-two tests that execute Plots against registered applications. Verify both response correctness and call graph conformance via the Signal Aggregator event stream.

**Signal Clearance** — SETI's authorization model. Wr4nglers hold clearances, not roles. Clearances govern which signal feeds a Wr4ngler can subscribe to. Administered by the Sec Wr4ngler.

**Plots Need Regeneration** — When a monitored application's contracts change, Plot Store flags affected Plots. Flagged Plots still execute but results are tagged as potentially stale. The Connie Wr4ngler is notified to regenerate before full confidence is restored.

## Running SETI

Requirements: Docker, Docker Compose.

```bash
git clone https://github.com/Pelentan/tca-seti
cd seti
cp .env.example .env
# Edit .env with cluster configuration
docker compose up --build
```

SETI self-registers in its own Policy Job on first run. Its own Contract Tests begin executing on the configured schedule automatically.

## Registering an Application

Applications are registered via the Policy Job admin API. SETI requires:

- Application identifier and display name
- Repository URL and contracts folder path (read access only)
- Gateway endpoint per environment
- Observability stream endpoint (`tca:events` Redis connection)
- Schedule configuration per test tier
- Failure response policy per Job and severity

---

## Methodology

SETI is built on Tessellated Constellation Architecture. Every Job has an OpenAPI 3.1 contract written before implementation. Jobs communicate via mTLS-authenticated REST. All inter-service calls are reported to the Observability Job via the `x-tca-observability` contract obligation. Security posture is defined per Job in `x-tca-security` contract blocks.

SETI's own Plots are the reference implementation for Plot generation in the TCA guidelines. The tool that defines the standard demonstrates the standard.

## Language and Dependency Constraints

### No Rust Dependencies
No TCA Job or supporting binary may introduce a Rust dependency, directly or transitively through a package. This includes Python packages with Rust extensions (e.g. `cryptography`, `pydantic-core`, `orjson`) and any npm package compiled from Rust. The Go standard library, Python standard library, and Node.js built-in modules are the correct tools for cryptographic operations. If a package requires Rust to build, find a different approach.

This constraint exists because Rust compilation introduces a toolchain dependency that is inconsistent with TCA's supply chain posture, and because packages with compiled extensions frequently fail in minimal runtime environments (distroless, scratch) in ways that are difficult to diagnose.

### The Binary Pattern
Cross-language operations (health checking, self-registration, certificate operations) are handled by small static Go binaries compiled with `CGO_ENABLED=0`. These binaries are copied into every container regardless of the container's primary language. This is the same pattern as `/healthcheck` — one implementation, available everywhere, no language-specific reimplementation.
